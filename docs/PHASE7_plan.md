## 1. What Phase 7 is, and is not

**In Phase 7** (the owner's list): a Docker image and how it is configured; a deployment target; whether run state needs more than memory and folders; whether one shared bearer token is still right; TLS; and a review of everything Phase 6 built against Section M, **now that it can be reached from outside the machine**.

**Not in this plan unless the owner says so:** the "Expanded evaluation" of the PRD row (see OD-27), Phase 8 extensions, a new model provider, any change to extraction, validation, calculation, rules, labelling, the memo or the report. The pipeline stays as it is.

Also found, not tied to a requirement number:

- **F-6. Restarts.** The server keeps run state in memory and must run as exactly one worker process; a second worker would split the state. A restart loses queued and running runs, and the caller then sees `404` for a run it was given an ID for (OD-32).
- **F-7. Retention.** Run folders and the response cache keep figures, quotes and page text indefinitely; there is no delete endpoint (a decision of Phase 6) and no clean-up. On a server that is a growing store of document-derived data (OD-33).
- **F-8. Reproducibility metadata.** `manifest.json` records the git commit through a `git` call in the source tree; in an image there is no repository, so the commit is recorded as unknown. Fix (step 1): read the commit from a build argument.
- **F-9. Results across platforms.** The earlier tuning and the golden files come from a Mac. A Linux image has other versions of Tesseract and native PDF libraries. The reproducibility promise (same inputs, same outputs) holds within one environment; across them it has to be shown. Action: run the golden and reproducibility tests inside the image (step 2) and record the OCR engine version the image uses.

## 4. Proposed design, by area

**4.1 Docker (step 2).** A multi-stage build: a builder stage with `uv` makes the environment from `uv.lock` (`--frozen`, no dev group), and a final stage on a pinned slim Python 3.12 image holds only what runs: the environment, the package, `prompts/`, `config/` (the shipped defaults), the DejaVu fonts (already in the package), `procps` or no `ps` at all (F-4), and Tesseract with the English data if OD-30 says so. It runs as a non-root user, with a read-only root file system and a small writable `tmpfs` for uploads, no added capabilities, `no-new-privileges`, one uvicorn worker, a `HEALTHCHECK` on `/health`, and the entry point `credit-intel-api`. A named list of paths is copied (never `COPY .`). Tagged with the commit; the commit is passed as a build argument (F-8).

**Settings and secrets.** Settings are the existing file plus the existing environment overrides: a read-only mounted `settings.toml` holds the limits; the two secrets arrive as environment variables from the platform's secret store or a root-only env file outside the repository, and are never in the image or the compose file. Folders are volume mounts (`/data/runs`, `/data/cache`), set by `CREDIT_INTEL_API_OUTPUT_DIR` and `CREDIT_INTEL_API_CACHE_DIR`. `docker compose` with an optional second service (the reverse proxy, 4.4) is the way to run it on one machine.

**4.2 Persistence (step 3, if chosen).** Today: run folders on disk (durable, the evidence) and job state in memory (lost on restart). Options are in OD-32. What changes under any option other than "none": a startup step that finds runs that were accepted but never finished and records them (so a caller gets "failed: interrupted", not `404`), and a fixed rule that the uploaded copy must outlive the process if a run is ever to be resumed (today it is deleted on the run's end and sits in a temporary directory that a restart wipes).

**4.3 Accounts and authentication (step 4, if chosen).** The shared bearer token is right for one owner on a private network. It is not right for several people, for attribution, for revocation, or for a browser. The options (OD-34) run from "keep one token and harden it" to "build accounts". Building password accounts is the largest and riskiest item in this plan (hashing, sessions, CSRF, lockout, reset); I recommend not building it, for the reasons in the OD.

**4.4 TLS (step 5).** The application should not terminate TLS itself: certificate issue and renewal are operations, not application logic. Options in OD-35: a reverse proxy in the compose stack, the platform's own front end, or a private network that encrypts the path. The application needs only to know it is behind a proxy: which forwarded headers to trust, which host name is public (for the origin check, F-5/e), and to send `Strict-Transport-Security` (OD-36).

**4.5 The review (step 7).** The table in section 3 becomes an evidence table in an exit summary: each finding fixed and tested, accepted with a reason, or deferred by the owner. Tools to find what I did not think of are OD-39.

## 5. What must not change

No change to extraction, validation, evidence, calculation, rules, labelling or the memo and report text. The files an image run writes for a document must equal those the command line writes on a laptop for the same input and cached reply, apart from the run ID and times and the engine versions recorded in the manifest (F-9); a test inside the image shows it.

## 6. How it would be tested

On this machine, offline: the Dockerfile and `.dockerignore` read as text by tests (no secret or private path can enter; non-root; pinned base; no `COPY .`; the commit argument; the health check); the code fixes (F-1, F-4, F-5, F-8 and the decided parts of persistence, authentication and the proxy settings) with unit and integration tests and mutation checks, as in every earlier phase. **On a machine with Docker, run by the owner (or one they name):** the image builds; the container starts as non-root with a read-only root; `/health` answers; one fake-provider run through the container writes the same `memo.md` and `results.json` as the command line; the golden and reproducibility tests pass inside the image; a container with too little memory ends a run with `E-INPUT-PARSE-LIMIT` and not by killing the container (F-4); the image contains no `.env`, `private/` or PDF (listed from the built image).

## 9. Risks to settle in the PRD draft

- **I cannot build or run the image here.** A bug in the image would not show until the owner runs it. The static tests and the in-image test list in section 6 are how that risk is bounded.
- **Memory.** An out-of-memory kill of the container ends every run. The sizing rule in SEC-12's row must be a stated requirement with a test of the failure mode, not a note.
- **Different platform, different results** (F-9). OCR and PDF native libraries differ; the reproducibility claim must be shown in the image, and the OCR caveat (unmeasured on held-out scans) stands.
- **A public endpoint that spends model money.** One leaked token is a spending and misuse risk until OD-34 is settled; the private-network demo (OD-28 (c)) is the way to avoid it.
- **Scope creep in authentication.** Passwords and sessions are the part of this phase most likely to be done badly; the proposal keeps them out.
